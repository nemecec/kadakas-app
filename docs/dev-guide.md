# Kadakas developer guide

This guide gives the rules for all work on Kadakas, by people and by AI agents.

## Product rules

- Kadakas is a clean-room CAD application for landscape architects. Its workflow and terms follow Vectorworks 2026, so Vectorworks users feel at home.
- Use only public information: help pages at app-help.vectorworks.net, product pages and the published shortcut list. Do not use the Vectorworks software itself.
- Write all text and code in your own words. Do not copy help text, icons or graphics. Do not use Vectorworks trademarks as names in the product.
- Before you design a feature, read `docs/research/vectorworks-public-features.md` and the related public help page. Match the tool modes, the parameters, the terms and the default keys.

Plug-ins (`docs/plugins.md`) are WebAssembly modules. The example plug-ins live in `plugins/raised-planter` and `plugins/stone-row` (an object and a tool), outside the workspace (it builds for `wasm32-unknown-unknown` with its own lock file). The tests use their committed modules in `crates/kadakas-plugin/tests/fixtures/` (`raised_planter.wasm`, `stone_row.wasm`); run `scripts/build-plugin-fixtures.sh` after you change the example or the ABI, and commit the new module.

Nothing below `api` depends on `script` any more: `io` runs its converter through `sys`.

- `kadakas-update`, `kadakas-launcher` and `kadakas-sign-manifest` are native only (files, sockets, processes, windows). They are not in the wasm check. Leave them out of the `cargo check ... --target wasm32-unknown-unknown` line, and do not make a wasm crate depend on them.
- The launcher holds no secret. It has public keys only (`crates/kadakas-launcher/trusted-keys.txt`). Private keys exist in CI secrets only. Signing code lives behind the `sign` feature of `kadakas-update`, and only `sign-manifest` and tests turn it on.
- UI logic that has no egui code (tools, picking, snapping glue, view state, keymap) belongs in `kadakas-ui-core`, so another UI program can reuse it. The app only converts egui input into ui-core events and draws. Do not add `egui` to ui-core.
- Put each feature in its own crate or module, for example `kadakas-io` for file formats and `kadakas-site` for terrain. Keep the interface small.
- Units, l10n, core, container, file, crs, plants, collab, render, site, annot, x3d, ui-core, plugin-abi, plugin, feedback, api and app must build for `wasm32-unknown-unknown` (the wasm check covers them). `crs` uses `proj4rs` without its default features on wasm, because the `aeqd` feature compiles C code. Keep file access, threads and GPU code out of the pure crates; put native-only code behind `#[cfg(not(target_arch = "wasm32"))]`.
- Load and save a `.kad` file as a stream (DOC-19): `Document::from_reader` on a file from `fsio::open_regular` (it checks the kind and the size, and caps the read), and `Document::write_pretty` into `fsio::write_atomic_with` (or `write_durable_with`). For bytes that are already in memory use `Document::from_slice`, which is faster than a reader. The size limit of a session (`SessionLimits::document_file_bytes`) is for agents, who cannot be asked. The files of a person never get a silent cap: the app asks above 500 MB (`kadakas_ui_core::open_limit`, `file_io::open_decision`), and every new way into a `.kad` file (a new dialog) must go through it. Drag and drop is not supported yet: it needs a prompt for unsaved changes first. Do not build the text of a whole document (`read_to_string`, `to_string_pretty`) or a `serde_json::Value` of it for a file. A big text in a document type (a picture) deserializes with a visitor that takes `&str`, so no second copy is made.

## File format

A document file has two forms, and both load the same model (DOC-20 to DOC-22). `kadakas-file` tells them by the first bytes (`sniff`): the ZIP signature, or `{`.

- **Container** (`.kad`, the default): a ZIP file made by `kadakas-container`. Entries: `document.json` (the drawing without the history, deflate level 1, pictures as `{"$blob": "<sha256>"}`), `blobs/<sha256>` (the text of each picture of 4 KiB or more, stored, once; the same text and hash as the blobs of collaboration), `history/` (`top.json`, `versions.json`, `newest.json`, `blobs.json`, or `raw.json`) and `manifest.json` (the last entry: every other entry with size and SHA-256). Other ZIP tools can read the file (the tests use Info-ZIP `unzip`, `bsdtar`, `ditto`, the Java stream reader and Python `zipfile`), but a file that is edited and zipped again is not supported: the manifest would not match. ZIP64 is read and written. An entry that the code does not know is kept by a save (with a note), so a newer writer that adds data coupled to `document.json` must raise the container `format_version`, so that an older program refuses the file. A fuzzer (`crates/kadakas-container/tests/fuzz_open.rs`) changes containers at random: run it longer after a change of the reader, `KADAKAS_FUZZ_SECS=120 cargo test --release -p kadakas-container --test fuzz_open -- --nocapture` (CI runs 60 s). `docs/doc-load-benchmark.md` section 4 has the sizes and the limits.
- **Plain JSON** (`.json`): one readable file, the pretty text of `Document`, pictures as base64 inline, the versions in the field `history`. For git, diffs and debugging. `file.save {format: "json"}`, `kadakas convert in out`.
- **Reading** a container goes through `kadakas_file::native::open_path(path, max_bytes, ReadMode)` (the app, `kadakas_api::files::open_document`) or `read_bytes` (bytes in memory, the browser). `ReadMode::Lazy` is for the document that a person works on: the pictures stay in the file (`PngData` and `BlobText` hold a `LazyBlob`) and the history waits (`Document::lazy_history`). `ReadMode::Eager` is for a library or an import: everything is read, and the result does not depend on the file. A hostile file is an error that names the entry, never a panic. Do not use `Document::from_reader` for a file of a person any more: it knows only the plain form.
- **Pictures in code.** Read a picture with `PngData::bytes()` / `ImageResource::data_text()` / `BlobText::text()`: they return a `Result`, because a lazy picture is read from the file and the file can have changed. Never read the field of a picture by `Deref` or by `.0` in new code. A picture in the file counts 0 in the memory of the session (`resident_len`). To make a picture, use `PngData::new(bytes)` or `BlobText::from(text)`.
- **Saving** goes through `kadakas_api::files::write_document(path, doc, &SaveSpec { form, keep, anchor, skip_missing })` (`anchor`: `Session::needs_anchor()`; `skip_missing` and `allow_overwrite` only after the person agreed: a headless host agrees by the consent token of the refusal (`kadakas_api::files::consent_by_token`), the app asks the person (`file_io::ask_save_without`, `ask_overwrite`)) (the app, `file.save`, the CLI) or `kadakas_file::native::save_path`. The document must come from `Session::document_for_save_in(container)`, which reads a history that still waits when it has to (a container save of an untouched document copies the entries as they are). Never serialize `session.editor.doc()` for a file: a history that waits is not in it. `keep` names the files the document was opened from (`Session::file_source`): their unchanged entries are copied without decoding. After the rename the sources move to the new file. The consent tokens are made by the session (`kadakas_api::consent`, `Session::issue_consent` and `redeem_consent`); a host never builds one. The session also keeps `Session::seen` (`kadakas_file::SeenFiles`), the stamps of the files it opened or saved: a host that writes a document file itself calls `seen.note(path)` after the write and checks `seen.changed(path)` before it (the app and `file.save` do).
- **Contexts.** The reference form of a picture is written and read through two scopes of the current thread (`kadakas_core::blob::with_blob_refs`, `with_load_source(source, LoadKind, f)`; a load keeps one copy for each hash, also for the plain JSON form: `with_intern_scope`), because serde has no context. Outside a scope a lazy picture is read and written as plain text, so `document.get`, collaboration and the JSON form need no knowledge of the container.
- **Tests of a new part of the file**: add a case to the hostile-container tests (`crates/kadakas-container/src/tests.rs`, `tests/behavior/test_container.py`) and keep the committed containers (`crates/kadakas-api/tests/data/container_golden*.kad`) reading. Make them again only on purpose (`cargo test -p kadakas-api --test container_golden make_the_files -- --ignored`), and say why in the commit.
- All document changes go through `Command` values. The GUI, the API and scripts use the same commands, so every change can be undone.
- When you add a `Shape` variant or an API method, keep the edits to shared files small and in one place.
- Agents must reach every document feature through the API. Add an example to `describe`.
- Agents file feature requests and bug reports with the `feedback` tool (`docs/feedback.md`). Keep the rule: no API method, MCP tool, flag or script approves an attachment. Only `Hub::approve` does, and only the app review and `kadakas feedback review` call it. The guarantee covers agents that are limited to MCP and JSON-RPC. An agent with a shell, or with scripts or converters allowed (`--allow-agent-scripts`, `--allow-converters`), runs as the same user and can edit the outbox files: say so, and do not hide it behind the terminal check. A restricted session never writes into the config, data and feedback folders (`PathPolicy`). A method that panics must not end a session: `Session::guarded` turns it into an internal error and marks the session tainted, and `Editor::execute` takes the changes of the command back first. Tests that touch feedback use `Hub::in_memory()`, a temporary folder or `KADAKAS_FEEDBACK_DIR`, never the folder of the user, and never the network.
- After you add or change a `Command`, renew its JSON Schema: `UPDATE_SCHEMA=1 cargo test -p kadakas-core --test command_schema`, and commit `crates/kadakas-core/tests/command_schema.json`. The schema comes from `schemars`; the types inside a command that other crates own (shapes, resource bodies, patches) are described in `crates/kadakas-core/src/schema.rs`.
- Unit patterns (pavers, tiles) are laid by `kadakas_core::layout`, which knows no object kind. A pattern is a set of cells on a lattice (`layout/module.rs`; the four bonds are built as such cells in `layout/bond.rs`), and a unit is its cell moved inward by half a gap. A new bond or preset goes in `bond.rs` or `module.rs` only. Keep the bounds in `layout/mod.rs` and `kadakas-io/src/dxf/export/patterns.rs` tied to a measurement: `cargo test -p kadakas-core --release layout::tests::measure_bounds -- --ignored --nocapture` and `cargo test -p kadakas-io --release --test pattern_export measure_export -- --ignored --nocapture` (set `MEASURE_BIG=1` or `MEASURE_SIZE=130x85`). Last measurement (release, 5,000 m2 box with an island, units of 200 x 100 mm and a gap of 5 mm, angle 11 degrees): running bond 233,000 units in 57 to 91 ms (list) with 22 MB of points; herringbone 233,000 units in 82 ms, gap lines 300 ms; basket weave 228,000 units; hexagon (across flats 200 mm) 86,000 units; octagon with square 173,000 units; I-shape 180,000 units in 61 ms with 40 MB of points. A 20,000 m2 box: 931,000 units of a bond in 0.15 to 0.2 s. A DXF export of 233,000 units is 60 MB in 0.85 s. The test fixture of the agent workflow is made by `tests/behavior/fixtures/make_parking_lot.py`. Regions from loose curves, zones, courses and the check sit on top of the engine and are tied to measurements in the same way: `cargo test -p kadakas-core --release --test pattern_plan_measure -- --ignored --nocapture` (bounds in `arrangement.rs`, `layout/zones.rs`, `layout/plan.rs`, `layout/check.rs`) and `cargo test -p kadakas-io --release --test pattern_blocks measure_blocks -- --ignored --nocapture` (blocks against polylines). Layout modules: `arrangement` (planar arrangement of lines and arcs: nodes, closed gaps, dead ends, faces with holes; under `regions`, PAT-06, and `layout/zones.rs`, PAT-07), `layout/course.rs` (a row of units along a path, PAT-08), `layout/plan.rs` (the zones and courses of a hardscape as data `pattern_plan`, and the groups that all consumers lay: the field, its zones and the courses), `layout/check.rs` (PAT-10). Everything that counts, lists or exports units of a hardscape goes through `plan::groups_of` / `plan::plan_groups`, never through the pattern and region of the object alone, so a zone or a course is never forgotten. Everything that draws them goes through `hardscape::draw` (`prepared` and `Prepared::draw`: PAT-12): the app canvas (`kadakas-app/src/plan_draw.rs`), `render.svg` (`hardscape::svg_extras`, with the region and `show_check` of a render in `SvgContext`) and the sheets (`kadakas-print/src/areas.rs`); never call `gap_lines` for a drawing of an object. The app lays plans and checks in the background (`plan_worker.rs`, one thread, latest job of a place wins; `PrepareJob` carries a small document, `Prepared::findings_cancellable` stops), keeps one plan per object (`plan_draw.rs`) and gives a compare ghost its own place; a new drawing path must not wait for a lay or a check on the window thread. The bounds of the level of detail (`CANVAS_BOUND`, `SVG_BOUND`, `PRINT_BOUND`) are tied to measurements: `cargo test -p kadakas-app --bin kadakas-app measure_canvas_frames -- --ignored --nocapture` (add `--config 'profile.dev.package.epaint.opt-level=3'` and the same for `egui`, `emath`, `ecolor` to get frame times like the release build), `cargo test -p kadakas-core --lib measure_bounds -- --ignored --nocapture` and `cargo test -p kadakas-print --test pattern_draw measure_pdf -- --ignored --nocapture`. Last measurement of these (release): 199,000 loose segments to 99,000 regions in 0.63 s (234 MB; 9,940 segments in 19 ms); a 5,000 m2 lot cut into 20 zones in 0.1 ms and laid in 37 ms (233,000 units as one area: 26 ms), 10,000 zones cut in 19 ms and laid in 0.34 s; a course along 1 km of kerb: 9,500 units in 1 ms straight, 0.3 s on a curve of radius 318 m (joints 5.00 to 5.14 mm); the check of 233,000 units in 0.45 s (1.7 s at 45 degrees) and 120 MB; the DXF of 233,000 whole units as INSERTs is 27 MB against 39 MB as polylines (37.5 MB against 60 MB on a pattern turned by 17 degrees), written in 0.30 s against 0.24 s. Zones that give their units by center (`plan::Owner`) share one `Shared` cache: the first zone that is asked lays the lattice and files each unit under its zone with a grid (`ZoneGrid`); the other zones read their list. Measure any change of it with `cargo test -p kadakas-core --release --test pattern_plan_measure measure_centroid_zones -- --ignored --nocapture`.
- The parameters of an API method are a Rust struct in `crates/kadakas-api/src/params/` (one file per domain; the module doc of `params/mod.rs` shows how to write one). serde parses and checks the call (types, required fields, allowed values), `#[serde(deny_unknown_fields)]` refuses an unknown name (the error names the nearest known one), and schemars makes the JSON Schema from the same struct: `describe {method}`, `describe {schemas: true}`, the MCP tools and the Python `TypedDict` classes (`python/tools/codegen.py`) all read it. Doc comments on the struct and its fields become the descriptions of the schema. A layer, class or sheet is a `LayerRef`, `ClassRef` or `SheetRef`: an ID or a unique name, turned into an ID when serde reads it. A new method or parameter needs a struct and an `entries!` line in its domain file; a test fails for a method without a struct and for a `describe` example that its struct refuses. Wrong parameters are errors (-32602) that name the parameter and what it expects, so a test of a refusal looks for the name of the parameter, not for a text of the method.
- After you add or change an API method, renew the Python package: `KADAKAS_BIN=<your binary> python python/tools/codegen.py`. The test `python/tests/test_drift.py` fails when `python/kadakas/_api.py` and `describe` differ.

## Many documents in one process

A host can run many `Session` values in one process (PLAT-12). The rules:

- A session owns all of its state. A library crate has no `static` with document data. A `static` is allowed for an id allocator (the editor revision, the GUID counter) or for a table that never changes.
- A big text in a resource (the file of a plant image) is shared text (`SharedText`, an `Arc<str>`): a clone is cheap and the check of equality stops at once for the same text. Do not read such a file at every change; read it where it first arrives and keep the answer (see `ImageResource::verify_data`).
- Every cache is per session and bounded: `RevCache` for one entry by revision, `LruCache` for many. The site analysis cache is in `SiteCache`, which `Session` owns.
- `SessionLimits` sets the limits of one session: objects, memory, undo history bytes, request time, render picture size, plant picture file size and pixels (`picture_bytes`, `picture_pixels`) and so on. `Session::set_limits` changes them. A call that changes the document and breaks the object or memory limit is undone. A session that is over the limit without a change only drops its caches, so reads and saves keep working. `document.load` and `file.open` refuse a document that does not fit before they replace the open one. The estimate counts the objects, the undo steps and the change log.
- Two process-wide values are explicit exceptions for the UI: the active language (`kadakas-l10n`) and the current units (`kadakas-units`). They are preferences of the person. They are not document data, and an API session never reads them.
- New ids are UUIDv7 (`Document::alloc_id`). A web build must call `kadakas_core::uid::set_host_seed(ms, salt)` once before it makes a document (the app does this in `new_web` with `Date.now()` and `crypto.getRandomValues`), because `std` has no clock or process there. Tests and fixtures use `Document::with_sequential_ids()` or `kadakas serve --sequential-ids`.

## Test-only features

A feature that only tests need must never be in a program that we ship. `kadakas-core` has `fault-injection` (a command can be made to panic, see `kadakas_core::fault`); only the dev-dependencies of `kadakas-api` turn it on. `scripts/check-test-hook.sh` reads the feature tree of `kadakas-app`, `kadakas-cli` and `kadakas-launcher` and fails if a hook is in it (and fails if it cannot see the hook in the tree of the tests). CI runs it (job `test-hooks`). Add the name of each new test-only feature to `HOOKS` in the script.

## Toolchain

- The minimum Rust version is 1.96 (`rust-version` in the workspace `Cargo.toml`). wasmtime 49 needs it. Use the current stable toolchain; CI uses `stable`.
- Raise `rust-version` only when a dependency needs a newer compiler, and then to the lowest version that works, not to the newest.

## The JavaScript engine (wasi-sdk)

`kadakas-api`, `kadakas-cli` and `kadakas-app` have the cargo feature `script-js` (on by default). It builds QuickJS to WebAssembly in `crates/kadakas-script-js/build.rs`, with the C compiler of **wasi-sdk 34.0**. The version and the SHA-256 of the archives are pinned in `crates/kadakas-script-js/wasi-sdk.env`. The build downloads nothing. The source is vendored (`crates/kadakas-script-js/quickjs/`, with the tag and hash in its `README.md`), and the build runs again only when the source, the flags, the toolchain version or one of the variables below change. Crates that do not use the engine (`cargo test -p kadakas-core`, and so on) build without wasi-sdk. For `kadakas-api`, `kadakas-cli` and `kadakas-app`, which turn the feature on by default, build with `--no-default-features` (give it for every one of these packages in the command, for example `cargo check -p kadakas-api -p kadakas-cli --no-default-features`; cargo joins the features of all packages of one command). The wasm check of the browser build needs the toolchain: it builds the engine. A build with the feature and without the toolchain stops with a message that names the version and these steps.

Install the toolchain once:

- **macOS and Linux:** run `scripts/install-wasi-sdk.sh`. It downloads wasi-sdk 34.0 for your system and processor, checks the SHA-256, installs it to `~/.local/share/wasi-sdk/34.0` (`--dest DIR` changes it) and prints the line `export WASI_SDK_PATH=...`. Put the line in your shell profile. The build also finds the default folder without the variable.
- **Windows:** download `wasi-sdk-34.0-x86_64-windows.tar.gz` (or `arm64`) from https://github.com/WebAssembly/wasi-sdk/releases/tag/wasi-sdk-34, check its SHA-256 against `wasi-sdk.env`, unpack it, and set `WASI_SDK_PATH` to the folder (it has a file `VERSION` that says `34.0`). Git Bash can run `scripts/install-wasi-sdk.sh`, as CI does.
- **Homebrew (macOS), instead:** `brew install llvm lld wasi-libc wasi-runtimes`. The build finds `llvm`, `lld` and `wasi-libc` with `brew --prefix`; `WASI_CLANG`, `WASI_WASM_LD` and `WASI_SYSROOT` name them by hand. The module that this makes may differ byte for byte from the module of the pinned wasi-sdk. CI and the releases always use the pinned wasi-sdk.

The build prints which toolchain it used (`cargo:warning=script engine: ...`), and `script.js_info` reports it. The finished module may import only `kadakas.call` and `kadakas.read`; the build fails if it imports anything else. CI installs the toolchain with the action `.github/actions/wasi-sdk`, which caches the toolchain and the finished module (`KADAKAS_JS_CACHE_DIR`; the file name has the hash of the source, the flags and the version, so an old entry is never used). 

Update the pinned version in one place, `wasi-sdk.env`: the version, the tag and all six hashes (the release page publishes them). To update quickjs-ng, follow `crates/kadakas-script-js/quickjs/README.md`.

## Quality rules

- Write unit tests for all logic. Add property tests (proptest) where random input can find bugs.
- Tests must not depend on the speed of the machine. CI runs them in debug builds, under coverage instrumentation and on busy runners, so a wall-clock limit fails by chance. Check the work done: count cache builds and hits (`SiteCache::analyses_computed`, `AnnotCache::builds`, `section_cache.builds`), geometry operations, shared instances (`Arc::ptr_eq`, mesh and instance counts) and output sizes. A test of a time limit (a script, a download or a converter that must be stopped) asserts the `Timeout` error, not the time it took. Waiting loops with a deadline are fine: they fail only when something never happens.
- A test where speed is the point is a perf test. Mark it `#[ignore = "timing test: run in release mode"]` and put it in `tests/perf.rs` or in a test whose name starts with `perf_`. CI runs the perf tests in release mode (job `perf`): `PERF_SIZES=10000 cargo test --release -p kadakas-core -p kadakas-container -p kadakas-site -p kadakas-api -p kadakas-io -- --ignored`. Run them yourself after you change a hot path. A new crate with perf tests goes in that command.
- Add Python behavior tests in `tests/behavior` for features that agents can reach through the API.
- DXF import and the parking lot workflow are tested on real-world mess: `tests/behavior/fixtures/messy/make_messy.py` writes a corpus of CAD-style files (LINE soup, bulges, old POLYLINE, SPLINE, ELLIPSE, HATCH, blocks, XREF, units, survey coordinates, Unicode layers, R12, R2018) and `expected.json`, and `test_messy_dxf.py` runs the whole workflow on each. When a real file breaks something, add a file that shows it to the corpus first, then fix the cause. Anything that is not imported must be in the import report with a reason (IOP-14). Seven files run by default (about 4 minutes in a debug build); the other 23 are marked `slow` (about 20 to 55 seconds each) and run with `KADAKAS_SLOW=1` or `pytest -m slow`. Run them once before a release and after any change to the importer, the layout engine or the zones.
- Keep line coverage of each library crate at 95% or more (`cargo llvm-cov -p <crate> --summary-only`). CI enforces it with `scripts/coverage.sh` (all crates, or name some: `scripts/coverage.sh print api`). The `kadakas-cli` crate has a bar of 90% (its tests run the binary). The app crate (egui and wgpu windows) is left out.
- Dependencies must have a permissive license. CI runs `cargo deny check` (settings in `deny.toml`). After you add or update a dependency, run `scripts/notices.sh` and commit `THIRD_PARTY_NOTICES.txt`; the installers ship it (`packager.toml`, `resources`).
- Attribution: every new dependency, asset (icon, font, image), dataset or cited formula or standard updates `docs/attribution.md`. Crates go in `THIRD_PARTY_NOTICES.txt` through `scripts/notices.sh`; other items go in `docs/notices-extra.txt`, which the script appends. Reviewers check this. Name a trademark only with its owner's note (see `docs/attribution.md`).
- Test helpers must run on Windows too: use `target/debug/kadakas.exe` there, and read pipes with a thread and a queue, not with `select`.
- Every text that a person reads in the UI goes in a `.ftl` file under `crates/kadakas-l10n/locales/en-US/`, with the Estonian text in `locales/et/`. In code, use `tr!("id")` and never a string literal in an egui call. A number that a person reads or types goes through `kadakas-units` (`current()` and `DragValueExt`). Do not write `format!("{:.1} mm", x)` in the UI. API and JSON-RPC texts stay English. `cargo test -p kadakas-l10n` is the CI check for this rule. See `docs/localization.md`.
- Workspace profiles (PLAT-04): a new key action, menu command or tool must work in every profile. Add a new `Action` to the Vectorworks-like defaults (`Action::defaults`); a profile file may leave it out and takes the default. Add a new menu command to `Cmd` in `profile/layout.rs` and to `default_menus`. A UI text that a profile may rename (a term such as "Class") stays a normal message; the overlay replaces it by id. Run `UPDATE_PROFILES=1 cargo test -p kadakas-ui-core` when the default profile changes, and commit `crates/kadakas-ui-core/profiles/vectorworks.json`. Built-in profile texts need en-US and et (`profiles/autocad.<tag>.ftl`); `cargo test -p kadakas-ui-core` checks them against the messages.
- Reject numbers that are not finite. Saved files must always open again.
- Plain English in documents and comments: short sentences, active voice.

## Checks before a commit

```
cargo fmt --all --check
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo check -p kadakas-units -p kadakas-l10n -p kadakas-core -p kadakas-container -p kadakas-file -p kadakas-crs -p kadakas-plants -p kadakas-props -p kadakas-review -p kadakas-collab -p kadakas-collab-ws -p kadakas-render -p kadakas-api -p kadakas-site -p kadakas-annot -p kadakas-x3d -p kadakas-ui-core -p kadakas-plugin-abi -p kadakas-plugin -p kadakas-script-js -p kadakas-feedback -p kadakas-app --target wasm32-unknown-unknown
cargo build -p kadakas-cli && uv run --with pytest --with ezdxf --with ifcopenshell pytest tests/behavior python/tests -q
uv run --no-project --with pytest pytest python/tests -q   # the Python package (set KADAKAS_BIN as for the behavior tests). Both folders also run in one command: pytest tests/behavior python/tests
```

All five must pass. The wasm check covers the app crate too: keep native-only code (files, threads, sockets, Python) behind `#[cfg(not(target_arch = "wasm32"))]`. The Python package tests belong to check 5. End each commit message with the co-author line that the project uses.

## Parallel work in worktrees

- Use your own build folder: `CARGO_TARGET_DIR=<repo main folder>/target-<feature>`. Shared build folders mix binaries from different branches.
- Disk space is limited. Set `CARGO_INCREMENTAL=0` and `CARGO_PROFILE_DEV_DEBUG=0`. Run release and coverage builds only when you need them.
- Point the behavior tests at your binary: `KADAKAS_BIN=$CARGO_TARGET_DIR/debug/kadakas`.
- Other branches add `Shape` variants, commands and API methods at the same time. Add catch-all arms where a match does not need every kind, and keep shared edits small.
- Before you finish, merge `main` into your branch, resolve conflicts, and run the checks again.
