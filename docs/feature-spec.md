# Kadakas Feature Spec

Kadakas is a clean-room, open-source CAD/BIM desktop app. A web build is a bonus. Its workflow and concepts match the latest Vectorworks (2026), so Vectorworks users feel at home. Landscape design is the first market.

Source of truth for Vectorworks behavior: `docs/research/vectorworks-public-features.md` (public pages only).

Priority: P0 = MVP, P1 = v1, P2 = later. Status: done = built and tested (in the core crate, the API crates or the app), planned = not built, deferred to Later = left out of v1 on purpose.

## 1. Goals and non-goals

Goals
- Let a Vectorworks landscape designer do real work with few surprises.
- Use the same concepts and terms: layers, classes, viewports, styles, record formats.
- Exchange data through open formats: IFC, DXF, GIS.
- Make every change scriptable and testable. AI agents are first-class users.
- Keep the core free of UI code. It runs in the desktop app, in the browser (WebAssembly), and headless.

Non-goals
- No copy of Vectorworks code, icons, help text, or exact UI art.
- No use of Vectorworks trademarks.
- No native `.vwx` support until legal review ends.
- No entertainment, lighting, or mechanical-engineering tools at first.
- No cloud service, accounts, or online project server in MVP.

## 2. Decisions

1. Stack: Rust, egui/eframe, wgpu. The core crate has no UI dependencies and compiles to WebAssembly.
2. Interop first: IFC (2x3, 4, 4x3), DXF, GIS (Shapefile, GeoJSON, georeferencing with WKT and EPSG). DWG goes through a converter program that the user installs (ODA File Converter or LibreDWG tools; `docs/dwg.md`).
3. Native `.vwx` is deferred pending legal review.
4. Terminology matches Vectorworks. Terms include design layer, sheet layer, class, viewport, Object Info palette, and Resource Manager. Others include record format, worksheet, data tag, site model, plant style, landscape area, and hardscape. Trademarks, icons, help text, and exact UI art are never used.
5. AI-agent control is first-class:
   - Every change is a serializable, undoable `Command`.
   - JSON-RPC 2.0 API over stdio (`kadakas serve`).
   - Same API over TCP to the live app (`--agent-port` or `KADAKAS_AGENT_PORT`). The app writes a random token and its port to a runtime file that only the current user can read. The first message on a connection must be `auth` with that token.
   - MCP server (`kadakas mcp`) for Claude Code.
   - SVG render so agents can see results.
   - A `describe` method for discovery.
   - Python package and scripts: see section 4.18. `view.screenshot` gives a PNG of the live window.
6. Testing: Rust unit and property tests. Python behavior tests over the JSON-RPC API. Line coverage of 95% or more for every library crate (cargo-llvm-cov, enforced in CI by `scripts/coverage.sh`; the CLI crate has a bar of 90%). CI on macOS, Linux, Windows.
7. License: Apache-2.0 OR MIT.

## 3. Concept glossary

| Term | Meaning in Kadakas |
|---|---|
| Document | One project file. Holds layers, classes, objects, resources, settings. |
| Design layer | Holds the model. 2D and 3D share one space. Has scale, elevation, lock, visibility. |
| Sheet layer | Holds a printable sheet with viewports and annotations. |
| Class | A named attribute and visibility group. A second axis next to layers. |
| Viewport | A view of design layers on a sheet layer. Has scale, render style, class/layer overrides. |
| Saved view | A stored set of layer and class visibility, camera, and phase. |
| Navigation palette | One palette for classes, layers, sheets, viewports, saved views. |
| Object Info palette | Shows and edits the selected object. Tabs: Shape, Data, Render. |
| Resource Manager | Browser for reusable resources: symbols, styles, hatches, record formats, worksheets, textures. |
| Record format | A user-defined set of fields attached to objects. |
| Worksheet | A spreadsheet that reads object parameters and records by criteria. |
| Report | A preformatted worksheet, such as a plant schedule. |
| Data tag | A label linked to an object. Shows chosen fields. Uses a tag style. |
| Data visualization | A rule that recolors objects by criteria. |
| Graphic legend | A sheet-layer table of object views or attributes. |
| Site model | A terrain surface built from source data and modifiers. Has existing and proposed surfaces. |
| Site modifier | An object that changes the proposed surface: pad, grade limits, grade object. |
| Grade limits | A closed boundary that limits where modifiers act. |
| Plant style | A reusable plant definition: name, ID, spread, height, symbols, database fields. |
| Plant tag | A label showing plant fields at up to three levels. |
| Landscape area | A polygon planted with mixed species by rate or percentage. |
| Hardscape | A closed area or path with a style (surface and components). |
| Existing tree | A surveyed tree with canopy spread, kept or removed. |
| Georeferencing | A coordinate system plus origin offset, stored per design layer. |
| Phase | A status (existing, new, demolished) on objects. Filters views and exports. |
| Command | One serializable edit. Executed through the editor. Always undoable. |
| Patch | The before/after record of a command. Powers undo and redo. |
| Agent API | JSON-RPC 2.0 interface that runs commands and reads state. |

| SIT-20 | Texture beds: site modifiers that give a closed region of the terrain its own texture (lawn, gravel, a path) without changing the grade. A bed is an object of kind `site_modifier` (modifier `texture_bed`) drawn with the Site Modifiers tool in its Texture Bed mode, made from closed shapes with Site > Create Texture Bed (`bed.add` with `from`: a closed polyline, closed 3D polyline, rectangle, circle, landscape area or hardscape; a landscape area with holes is refused), or added with `bed.add` and a boundary. API `bed.add`, `bed.set`, `bed.get`, `bed.list`; Object Info shows the material and an own mapping. **Texture**: the material in `texture` (a material resource), else the material of the slot of the bed object, else the material of its class ("by class"); a bed without a material has no effect, so the beds behind it and the look of the site model show. **Mapping**: a planar projection from above in world units; the tile size, offset and rotation of the bed (`own_mapping`) or else those of the site model. A moved bed takes its own mapping with it, and the offset is reduced to one repeat in the frame of the texture (so it stays in range and no pixel changes); a reprojection moves and turns it like the texture of a site model. Rotate, mirror and scale are refused for texture beds, as for all site modifiers (use `move`). `own_mapping: false` with `tile_size`, `offset` or `rotation` is a validation error. **Stacking order** is the drawing order of the document, so `arrange` (front, back, forward, backward) sets which bed wins where they overlap. **Surface cut**: a bed acts on the site models on its layer whose box touches it; it must be displayed (layer, class and the phase display rules, `Document::is_displayed`), on the proposed surface (the existing surface when the model has no modifiers). The triangles are cut along the outlines (module `kadakas_site::bed`): an outline edge that crosses a triangle cuts it along its line, and a piece goes to the frontmost bed that holds its middle (even-odd rule), else to the base. The pieces cover each triangle exactly once, the heights do not change, and cut points on an edge of the mesh are shared by both neighbors, so there are no cracks, and the pieces get the normals of the whole surface, so shading has no seam along an outline (with the elevation look the band edges keep the seams they had). A T-junction can remain where an outline corner lies exactly on a mesh edge; the point is on the edge, so there is no gap. The work is bounded: at most 64 beds per site model (the frontmost; the boxes are checked first and only those beds are flattened), 4096 points per outline (each flattening stops at the limit; curves are flattened coarser to fit), a grid that registers each outline edge only in the cells it crosses (at most 131 072 entries per outline) finds the edges near a triangle, an explicit stack instead of recursion, a budget of 200 million counted steps, 4096 cuts per triangle and 2 million output triangles. When a bound is reached while a triangle is cut, the whole source triangle goes to the base (never half-cut pieces) and the cut reports `truncated`. A bed does not change the proposed surface, cut and fill, contours or IFC (the exporter lists it as skipped). **Render and exports**: the pieces of a bed are mesh parts (`PART_BED + n`) of the site model, so the Look, the CPU and GPU renderers, `render.png`, glTF, GLB and OBJ with MTL use the same material and texture coordinates as other materials; with the elevation look the bands stay outside the beds. **Collab**: the bed is part of the `shape` property; a bad mapping or more than 4096 points puts the object in quarantine. A file with a bad mapping loads with the mapping reset, and a file with more than 4096 boundary points loads with the boundary thinned to corners (both in `notes` of `document.load`). A bed of a kind that an older version does not know stays as an unknown shape there. A bed counts as a user of its material (Resource Manager, purge), and so does the texture of a site model. **Not built:** a bed that blends with its neighbors, and a bed for the existing surface only. | P1 | done |

## 5. Non-functional requirements

- Performance: draw 100,000 simple objects at 60 fps pan and zoom on a mid-range laptop.
- Performance: a command on a small selection completes in under 10 ms.
- Determinism: the same command list on the same document always gives the same result.
- Safety: a failed command or batch leaves the document unchanged.
- Portability: core builds for native and `wasm32-unknown-unknown`. No threads or file access in core.
- Platforms: macOS, Linux, Windows desktop. Web build is best effort.
- Accuracy: use 64-bit floats. Document units and tolerances in one place.
- File safety: write files atomically. Keep a backup on save.
- Accessibility: keyboard access for all tools. Scalable UI text.
- Localization: all UI text goes through one string table. English first.
- Quality: core line coverage of 85% or more. Property tests for geometry and undo.
- Docs: every API method appears in `describe`.
- Privacy: no telemetry in MVP.
