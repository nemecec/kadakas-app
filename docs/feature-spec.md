# Kadakas Feature Spec

Kadakas is a clean-room, open-source CAD/BIM desktop app. A web build is a bonus. Its workflow and concepts match the latest Vectorworks (2026), so Vectorworks users feel at home. Landscape design is the first market.

Source of truth for Vectorworks behavior: `docs/research/vectorworks-public-features.md` (public pages only).

Priority: P0 = MVP, P1 = v1, P2 = later. Status: done = built and tested (in the core crate, the API crates or the app), planned = not built, deferred to Later = left out of v1 on purpose.

## 1. Goals and non-goals

Goals
- Let a Vectorworks landscape designer do real work with few surprises.
- Use the same concepts and terms: layers, classes, viewports, styles, record formats.
- Exchange data through open formats: IFC, DXF, GIS.
- Make every change scriptable and testable. AI agents are first-class users.
- Keep the core free of UI code. It runs in the desktop app, in the browser (WebAssembly), and headless.

Non-goals
- No copy of Vectorworks code, icons, help text, or exact UI art.
- No use of Vectorworks trademarks.
- No native `.vwx` support until legal review ends.
- No entertainment, lighting, or mechanical-engineering tools at first.
- No cloud service, accounts, or online project server in MVP.

## 2. Decisions

1. Stack: Rust, egui/eframe, wgpu. The core crate has no UI dependencies and compiles to WebAssembly.
2. Interop first: IFC (2x3, 4, 4x3), DXF, GIS (Shapefile, GeoJSON, georeferencing with WKT and EPSG). DWG goes through a converter program that the user installs (ODA File Converter or LibreDWG tools; `docs/dwg.md`).
3. Native `.vwx` is deferred pending legal review.
4. Terminology matches Vectorworks. Terms include design layer, sheet layer, class, viewport, Object Info palette, and Resource Manager. Others include record format, worksheet, data tag, site model, plant style, landscape area, and hardscape. Trademarks, icons, help text, and exact UI art are never used.
5. AI-agent control is first-class:
   - Every change is a serializable, undoable `Command`.
   - JSON-RPC 2.0 API over stdio (`kadakas serve`).
   - Same API over TCP to the live app (`--agent-port` or `KADAKAS_AGENT_PORT`). The app writes a random token and its port to a runtime file that only the current user can read. The first message on a connection must be `auth` with that token.
   - MCP server (`kadakas mcp`) for Claude Code.
   - SVG render so agents can see results.
   - A `describe` method for discovery.
   - Python package and scripts: see section 4.18. `view.screenshot` gives a PNG of the live window.
6. Testing: Rust unit and property tests. Python behavior tests over the JSON-RPC API. Line coverage of 95% or more for every library crate (cargo-llvm-cov, enforced in CI by `scripts/coverage.sh`; the CLI crate has a bar of 90%). CI on macOS, Linux, Windows.
7. License: Apache-2.0 OR MIT.

## 3. Concept glossary

| Term | Meaning in Kadakas |
|---|---|
| Document | One project file. Holds layers, classes, objects, resources, settings. |
| Design layer | Holds the model. 2D and 3D share one space. Has scale, elevation, lock, visibility. |
| Sheet layer | Holds a printable sheet with viewports and annotations. |
| Class | A named attribute and visibility group. A second axis next to layers. |
| Viewport | A view of design layers on a sheet layer. Has scale, render style, class/layer overrides. |
| Saved view | A stored set of layer and class visibility, camera, and phase. |
| Navigation palette | One palette for classes, layers, sheets, viewports, saved views. |
| Object Info palette | Shows and edits the selected object. Tabs: Shape, Data, Render. |
| Resource Manager | Browser for reusable resources: symbols, styles, hatches, record formats, worksheets, textures. |
| Record format | A user-defined set of fields attached to objects. |
| Worksheet | A spreadsheet that reads object parameters and records by criteria. |
| Report | A preformatted worksheet, such as a plant schedule. |
| Data tag | A label linked to an object. Shows chosen fields. Uses a tag style. |
| Data visualization | A rule that recolors objects by criteria. |
| Graphic legend | A sheet-layer table of object views or attributes. |
| Site model | A terrain surface built from source data and modifiers. Has existing and proposed surfaces. |
| Site modifier | An object that changes the proposed surface: pad, grade limits, grade object. |
| Grade limits | A closed boundary that limits where modifiers act. |
| Plant style | A reusable plant definition: name, ID, spread, height, symbols, database fields. |
| Plant tag | A label showing plant fields at up to three levels. |
| Landscape area | A polygon planted with mixed species by rate or percentage. |
| Hardscape | A closed area or path with a style (surface and components). |
| Existing tree | A surveyed tree with canopy spread, kept or removed. |
| Georeferencing | A coordinate system plus origin offset, stored per design layer. |
| Phase | A status (existing, new, demolished) on objects. Filters views and exports. |
| Command | One serializable edit. Executed through the editor. Always undoable. |
| Patch | The before/after record of a command. Powers undo and redo. |
| Agent API | JSON-RPC 2.0 interface that runs commands and reads state. |

| DOC-19 | Streaming load and save of `.kad`. Load parses from a buffered reader (`Document::from_reader`), so the whole file text is never in memory, and there is no `serde_json::Value` copy of the document. Bytes that are already in memory (the browser's file picker) use `Document::from_slice`. The limit depends on who opens the file, because a limit on the data of a person must ask the person, and a hard limit belongs in contexts that cannot ask. *Agents and API sessions* cannot be asked, so they have a hard limit, `SessionLimits::document_file_bytes`: 512 MiB by default (the document limit of the paid collaboration tier) and 32 MiB for `SessionLimits::strict()` (the snapshot limit of the free tier). Above 500 MB (decimal: 500 000 000 bytes; the texts use decimal MB and GB) the app asks before it opens the file: "This file is N MB and needs about M GB of memory to open. Open it?" with Open and Cancel; M is 1.7 times the file size (`kadakas_core::open_estimate`). The question is a modal window. A second question while one is open waits in a queue, and a file that grew after the person said Open is asked about again. It refuses only when that estimate is more than the physical memory of the computer (`kadakas_sys::sysinfo::physical_memory`: `hw.memsize` on macOS, `/proc/meminfo` on Linux, `GlobalMemoryStatusEx` on Windows); when the memory is unknown it never refuses and only asks. The question and the refusal are in en-US and Estonian and apply to File > Open, the library browser (the path goes through the path policy of the session before its size is measured) and the recovery of an autosave (the largest version decides). Opening a file by drag and drop is a future item. It needs a prompt for unsaved changes first, because a drop replaces the open document. Any new way to open a file of the person must go through `file_io::open_decision`. *The local commands of the CLI* (`kadakas import --into`, `export`, `render`) are run by the person, so they have no hard cap either: they refuse a file only when its estimate is more than the physical memory. *With `--connect`* the app decides: `file.open` from an agent in the app uses the limit of the app session (512 MiB, a hard limit; there is no preference for it yet), and the files that the person opens in the app are asked about. The numbers come from `docs/doc-load-benchmark.md`: a loaded drawing needs 1.1 to 1.7 times the file size in memory, and a 1.08 GB file opens in 8.5 s with about 1.8 GB resident. **A container (DOC-20)** is limited by what it holds and not by its size on disk: the limits of an agent apply to the file size and to the sum of the sizes of all entries, uncompressed, from the manifest (and to each entry), so a small file cannot hide a big document, and the error names the limit and the flag to raise it. The question of the app comes when the drawing and the history in the container (`document.json` and `history/`, uncompressed) are above 500 MB, because the pictures stay in the file; the question still names the size of the file, and the estimate of the memory is 1.9 times those bytes (`kadakas_core::open_estimate::needed_bytes_container`, from the measurements of `docs/doc-load-benchmark.md` section 4). The plain JSON form keeps 1.7 times the file size. The local commands of the CLI use the same estimate. The browser build has no file to check first, and its memory is unknown: it asks the same question for the bytes of the picker above 500 MB (`decide(len, None)`, so it only asks, never refuses on memory). Below a guard of 2 GiB (`file_io::WEB_GUARD_BYTES`) it never refuses; the guard is there because a wasm page cannot hold more. The nesting depth (128), the counts and the repairs and notes of the load keep their checks. **Duplicate keys.** A known field that appears twice in a file (for example two `layers`, or two `format_version`) is refused with a clear error; the old reading took the last value. **Other paths.** The autosave writer thread, the app, the CLI and the library files use the streaming writer; the autosave copy of the "save over my file" option is written outside the lock and only the check and the rename are under it. The browser build has no files: it parses the picker bytes with `from_slice` (with the same size limit) and its save builds the bytes for the download. `document.get` and `document.load` still use JSON values, and collaboration does not load `Document` JSON at all (it syncs operations and parts). A test counts the peak extra bytes for a small document (always) and for 200k objects with a 20 MB picture (`kadakas-core/tests/stream_load.rs`, `--ignored`). | P1 | done |
| DOC-20 | Container file format. A `.kad` file is a ZIP container (the crate `kadakas-container`: our own reader and writer over `flate2` and `sha2`, so there is no new dependency (the choice against the `zip` crate is in `docs/attribution.md`); stored or deflate entries, never encrypted; ZIP64 is read and written when a count is above 65 534 or an offset or a size is above 4 GiB less 2 bytes; at most 250 000 entries; a document over that is refused before anything is written, with an error that suggests the JSON form). **Entries.** `document.json`: the drawing as pretty JSON without the history, deflate level 1; a picture or other big text of 4 KiB or more is the reference `{"$blob": "<sha256>"}`. `blobs/<sha256>`: the text of the picture, stored as it is, once: the same text and the same hash as the blobs of collaboration (the base64 text of the PNG of an underlay, the base64 file of an image resource, the compact JSON of the `recs` of an import base, IOP-22); the name is the hash and is checked. `history/`: the version history of REV-01 as `top.json`, `versions.json`, `newest.json` and `blobs.json` (the hashes of its pictures, which are entries of `blobs/` and are shared with the drawing), or `raw.json` for a history of any other shape (kept whole and never changed). `manifest.json`, the last entry: `format` `kadakas-container`, `format_version` 1, `generator`, and every other entry with its `name`, `size` (uncompressed) and `sha256`. Other ZIP tools read the file (tested with Info-ZIP `unzip -t`, `bsdtar -tf`, `ditto -x -k`, the stream reader of Java and Python `zipfile`, also in the ZIP64 form); a file that is edited with such a tool and zipped again is not supported (the manifest would not match). A stored entry has its CRC-32 and sizes in the local header (the stream reader of Java refuses a data descriptor there); a streamed entry has a data descriptor with 32 bit sizes (64 bit from 4 GiB). An entry of the manifest can have a `role` (the blob with the summaries of an import base has `import_base_recs`, which the estimate of the memory of an open counts, because that text is parsed at the open). `history/anchor.json` and `history/anchor-blobs.json` hold the drawing that the versions were saved with, when a save of an edited document wrote the versions as they are (DOC-21). **Entries that this version does not know** (a newer program may add them) are kept by a save and counted in a note of the save, never dropped silently, also names under `history/`: a newer program that writes data that depends on `document.json` must raise `format_version` (the container version of the manifest), so that this version refuses the file instead of keeping data that no longer matches the edited drawing. A streamed entry that may pass 4 GiB (a drawing estimated at 3 GiB or more) has the ZIP64 field in its local header (version 45) and a 64 bit data descriptor (APPNOTE 4.3.9.2); a smaller one has none and a 32 bit descriptor. A **fuzzer** (`crates/kadakas-container/tests/fuzz_open.rs`, stable Rust, seeded with the committed containers and containers made in the test, a time budget in `KADAKAS_FUZZ_SECS`, 60 s in the CI job `fuzz`) changes containers at random and opens them and reads every entry: nothing may panic or take long. The same content gives the same bytes (fixed time stamps). **Reading is bounded** (`kadakas_container::Limits`, checked before a body is read; each fault is an error that names the entry and never a panic): at most 250 000 entries; the central directory at most 64 MiB and the manifest at most 128 MiB; names are plain relative paths and unique (no empty, `.` or `..` part, no leading `/`, no `\`, no control character, at most 255 bytes); only stored and deflate; no encryption, no split file (ZIP64 is read, with its end records and extra fields); each entry and all entries together at most the limit of the caller (`SessionLimits::document_file_bytes` for an agent); a blob is at most 128 MiB as text (the largest picture of an underlay, 4096 x 4096 pixels of noise, is a PNG of 64.0 MiB and 85.3 MiB as base64 text; a save refuses a bigger text before it writes anything, so a file that Kadakas writes always opens; an end record whose 32 bit fields are not "see the ZIP64 record" must say the same as the ZIP64 end record, a second ZIP64 extra field is refused, and the number of the disk is read from the ZIP64 field when the 32 bit field says so (a comment of up to 65 535 bytes after the end record is found; the ZIP64 record is found through the locator that stands right before the end record); the entries are disjoint (an entry that overlaps another is refused); a stored entry is checked while it is copied; the local header must agree with the directory (name, method, not encrypted, and CRC-32 and sizes when they are not left to a data descriptor). The numbers come from `docs/doc-load-benchmark.md` section 4 (a real document inflates 6.8 times, the most repetitive legal one 110 times, zeros 1 000 times; the most entries give a directory of 11.7 MB). A damaged container never opens in part: the error names the file and the entry. | DOC-21 | Lazy parts: pictures and the history stay in the file until they are needed and are read by hash. **Pictures.** The picture of an underlay (`PngData`) and the file of an image resource (`ImageResource::data`, a `BlobText`) are in memory or a handle (`kadakas_core::blob::LazyBlob`: the hash, the size, the first 8 characters and the open file). File > Open, `file.open`, the CLI and the browser open a container lazily. The text is read by hash when a program uses it (a render, `plant_style.get_picture`, a save to JSON), checked against the hash, and not kept (a weak cache: the last user frees it). A library or an import reads the pictures at once (`ReadMode::Eager`), so the result does not depend on the file. **The history** waits in the file (`Document::lazy_history`) until a call uses it: the Versions window, a compare, a restore, any `version.*`, a render with `compare`, a save to JSON, or a save after an edit. Then the session (`review_api::resolve`) reads the entries, checks them against the drawing as the file holds it (the document in memory if nothing changed since the open, else the drawing read again from the file; a file of an older version that got a project GUID in memory counts as changed) and puts the history into the document without an undo step. If the entries cannot be read (the file changed, an entry is damaged) the history stays in the file as it is: it is read only (`history_read_only`, the note names the entry), no version is made, restored or deleted, and `version.repair {confirm: true}` is the only way to drop it; it keeps every version that can be read (the entries are read as they are and checked against the best drawing there is) and is one undo step, except when the entries cannot be read at all (then nothing is kept and the answer says `undoable: false`). A failed try is remembered with the revision and the state of the file, so the drawing is not read again for each call. **A save never reads the versions just to write them again and never stops because of them**: a container save of a document whose versions wait copies their entries as they are, and, if the drawing was edited, writes the drawing of the file as their anchor (`history/anchor.json` with the list of its pictures in `history/anchor-blobs.json`; `Session::needs_anchor`, `WriteOptions::anchor`); a file with an anchor entry reads its versions against that drawing, and the next save after the versions were read writes them in the usual form again. The plain JSON form needs the versions inside: if they cannot be read it asks the person (see below). **The open file.** `FileSource` keeps the path, the directory and the manifest with its hash, and opens the file again for each read (no handle stays open, so the rename of a save is never blocked, also on Windows). **The content is the authority, not the stamp of the file** (size, time of change). A part is known by its name and its SHA-256. If the stamp differs, the source opens the file again and compares the hash of the manifest: the same hash (a touch, a copy, a backup tool) takes the new stamp and goes on. If the file is another file, a part is still read when the file at the path, or the `.bak` of the last save, has an entry of that name with the same SHA-256; every part is checked against its hash, and a blob is found by the hash that is its name. Only the drawing (`document.json`, and the anchor of the versions) is read as a stream from a file that has an entry with the hash it had at the open. A part that no file has is `parts_missing` (below), and an entry error of a file that turned out to be another file says "changed on disk" (code 5), not a complaint about a local header. **Save.** It copies the entries that did not change from the old file without decoding them (`Writer::copy_raw`: the compressed bytes with the CRC-32 and the hash of the old manifest; a stored entry is checked while it is copied): every picture that is still a handle, the pictures of the history that waits, each history part that is equal (same SHA-256), and the entries that a newer program added (they are kept, not dropped). A picture that is in memory is written from memory, also when an old file has it too (the file may have changed). A picture that the drawing no longer has, but that an undo step still holds, is kept in the new file; a save over the file keeps it too (the autosave passes the sources of the session, so the undo step does not lose its picture), and the set of live handles keeps all handles of a hash (the read of the anchor makes handles that are not noted). **Before anything is written** the save counts the entries and the size of every text against the limits of the format (a picture of more than 128 MiB as text, or more than 250 000 entries, is `FileError::Limit` with a message) and looks for every part it must copy; what no file has is `parts_missing`: code 5, `data.missing` {file, pictures, history, other}, `ask_the_person`, nothing written. **The person decides.** `file.save {allow_missing: <consent_token>}` (the token is in the refusal, `data.consent_token`: an HMAC-SHA-256 with a random secret of the session over the kind, the facts of the refusal and a nonce, so nobody can compute it without having seen the refusal; it is good for one save, it is used up when it is redeemed, a save ends all tokens, and an edit, another open file or a new document makes it stale; a bare `true`, a made up token, one used before and the token of another kind or another refusal are refused; the app asks the person, whatever an agent passes, default No) saves the rest: the missing pictures become one pixel gray placeholders (and the session refers to them from then on), the versions that cannot be found are left out, parts that only an undo step or a newer program needs are left out and counted; the placeholder change is one undo step (the undo brings back the handles of pictures that no file has; a later save does not ask again for them, because a picture that only an undo step holds never stops a save: it is left out, and the reply says once, and again only when the number changes, "N picture(s) that only undo could bring back are no longer in any file; undo will show them empty"). The first time a save, or a check of the file, finds that the file is another file, the pictures that a handle still uses (the drawing and the undo steps) and that some file still has (the file or its `.bak`) are read into memory then (`FileSource::rescue_if_changed`), so a second save by another program, which replaces the `.bak`, cannot take the last copy away; they are written from memory. Only that moment reads them, so the laziness of an unchanged file is kept, and each placeholder keeps the hash of its picture in `source` (`missing:<hash>:<the old source>`): the load says that there are placeholders, nothing writes the gray pixel as if it were the picture, and a file that has the real picture again (by its hash, in the file or its `.bak`) puts it back at the open, with a note, after the same checks as for any underlay or image (at most 4096 pixels a side, a PNG or JPEG; a picture that fails stays a placeholder, with a note); a relink at the open arms the history that waits with `exact = false`, because the drawing is not the drawing of the file, so the versions are not made read only by mistake. The reply has `notes` (`file.save` returns the notes of every save, DOC-22). **Another program's file.** A save over the file at the path compares the manifest of that file with the one of the file that was opened; if they differ (two instances, a sync conflict copy) nothing is written: `file.save` answers code 5, reason `file_changed`, `ask_the_person`, `consent_token`, and `allow_overwrite: <consent_token>` (the app: "changed by another program since you opened it, overwrite?", default No) replaces it, the old file staying as the `.bak`. A touch or a copy with the same manifest is no change. **Every path is guarded, in both forms**: the session keeps a content stamp for each file that the document was opened from or saved to (`kadakas_file::SeenFiles`: the hash of the manifest for a container, the hash of the whole file for the plain JSON form), the save compares it before the replace, and its own write and the autosave over the file note the new stamp; a path that was never seen has no guard, a deleted file is no change. The autosave over the file skips (the message says so, the recovery copy is written) instead of replacing such a file. The atomic save is unchanged (temporary file, flush, fsync, rename, fsync of the folder, `.bak`); a failed save leaves the old file as it is and no temporary file. **Saving over the file that the lazy parts read from works**: the copy reads the old file while the temporary file is written, the rename comes last, and then the sources move to the new file (`FileSource::rebind`): the pictures are found by hash, and the move happens under the lock of the manual saves when an autosave writes over the file. After a save to another path the document reads from the new file, so the old file may go. Browser: the picked bytes stay in memory and the pictures are read from them; the download is a container (`file_io::container_bytes`). **Measured** (`docs/doc-load-benchmark.md` section 4, the 106 MB and 1.08 GB documents): the container is 3 times smaller; the lazy open has 14 to 17 percent less heap and the same time; the save with 92 pictures copies 245 MB without a codec; the deflate of `document.json` costs about 5 s of CPU for 838 MB of text, so a save of a huge drawing takes longer than the plain save. #### Unit patterns (PAT)

A unit pattern lays equal units (pavers, tiles, boards, bricks) in a bond, or the unit shapes of a module, over a closed region. The engine knows nothing about hardscapes: it takes a region, a pattern and a placement. Hardscapes use it for their joint pattern (HRD-08), and the API works on any closed shape.

## 5. Non-functional requirements

- Performance: draw 100,000 simple objects at 60 fps pan and zoom on a mid-range laptop.
- Performance: a command on a small selection completes in under 10 ms.
- Determinism: the same command list on the same document always gives the same result.
- Safety: a failed command or batch leaves the document unchanged.
- Portability: core builds for native and `wasm32-unknown-unknown`. No threads or file access in core.
- Platforms: macOS, Linux, Windows desktop. Web build is best effort.
- Accuracy: use 64-bit floats. Document units and tolerances in one place.
- File safety: write files atomically. Keep a backup on save.
- Accessibility: keyboard access for all tools. Scalable UI text.
- Localization: all UI text goes through one string table. English first.
- Quality: core line coverage of 85% or more. Property tests for geometry and undo.
- Docs: every API method appears in `describe`.
- Privacy: no telemetry in MVP.

### 4.22 Review and versioning

Humans and AI agents review a model through the same data. Humans get a visual form, and agents get structured JSON first and images second. Ideas come from public descriptions of other tools: named versions and a full edit history (Onshape), comments pinned on the canvas (Figma), a colored compare of versions (Revit with Autodesk Construction Cloud), and issues with a viewpoint (BCF, the BIM Collaboration Format of buildingSMART International, an open standard). Vectorworks users mostly review with Project Sharing history, PDF markup and BCF. Kadakas is not affiliated with Vectorworks, Inc. or with the makers of these tools.

| ID | Feature | Pri | Status |
|---|---|---|---|
| REV-01 | Named versions and local history. `version.create {name, note?}` saves a snapshot of the document with author, time and origin (user, agent, script, remote). The `.kad` file keeps the versions and the edit log between them, with caps for the count and the total size (the oldest unnamed points go first). `version.list`, `version.get` (read-only document), `version.restore` (one undo step, the current state stays as a version). Pure code in a new crate `kadakas-review`. | P1 | done (v1): the crate `kadakas-review` (pure, wasm-compatible) with the version store. **The drawing is the only full copy in a file.** The newest version is stored as a change from the drawing (made again at each save, one comparison of the drawing with the newest version), and each older version is a reverse delta of property operations from the next newer version on its first-parent chain (the property model of collaboration, now in `kadakas-props`). There is no separate base snapshot. To open version k the code starts at the newest version and applies the deltas backwards. Deleting any version joins its two neighbor deltas, and every other version stays exact. The `.kad` file keeps this in the optional field `history` (`format` 2; the file format version of the drawing stays 3, a file without it loads). The file form has `newest.delta` and `newest.anchor` (a digest of the drawing); a save also writes the stacking keys of the drawing into its objects and layers, so that the drawing gives the same state when it is read again. The drawing never needs the history to load: the history is read afterwards and only when it is used (the open document and its undo steps hold the history as one JSON value against an anchor, the drawing as it was when the history was opened or started, which the session keeps once; so a version costs a delta, not a copy of the drawing, in memory). Big values that collaboration also keeps as blobs (the picture of an underlay, the picture of a plant style or an image resource, and the summaries of a DXF import base, IOP-22) are stored once by hash (reference counted) in the history; a picture that the drawing holds is not repeated in the file. A version has an ID (a number, never reused), a name, an optional note, an author, a time (`now_ms`; 0 when a host has no clock), the origin of the editor (user, agent, script, remote), the editor revision when it was saved, `parents` (a list, first parent first) and a `branch` (default `main`); the history has a current `branch` and a `head`, so branches (REV-10) need no change of the file. **No version is dropped without the consent of the person.** There is no automatic folding or eviction. `SessionLimits.max_versions` and `max_version_bytes` (File > Preferences > Versions) are thresholds: a `version.create` (or the automatic version of a `version.restore`) that would go over one is refused, nothing is changed, and the error (code 6, `data.kind` limit, `data.reason` `version_limit`, which is in the answer on the wire and in the text of an MCP tool error with the list of versions) lists the versions with id, name, size, time and auto; the describe texts tell an agent to pass this to the person. A history that could not be read completely (a damaged part, over a bound, a drawing that does not match the one the versions were saved with, nonsense in the field) is opened as it is: the document loads, the history stays unchanged in memory, a save writes the versions back unchanged and adds the entry `base` (the changes from the saved drawing back to the drawing that the versions were written against, with the pictures they need), so that no version is lost when the drawing is edited and saved, the load notes say why (`document.load` and `file.open` return `notes`; the app shows them). **Nothing is rebuilt from a drawing that is not exactly the one the versions were saved with** (the digest of the anchor must match; another program, or a newer program that reads a file in another way, can make it differ in one detail): that would change the content of versions without the person. The note says that the drawing does not match the one the versions were saved with and gives the count of versions; it also says how many versions a repair would delete (`version.list` has `unreadable_versions`; the app button says the count), and the history is read only (`version.create`, `restore` and `delete` fail with a conflict, `data.reason` `history_read_only`) until the person calls `version.repair {confirm: true}`, which keeps the readable part and is one undo step. `version.create`, `version.restore` (the current state is saved first as an automatic version, unless it equals the newest version; then the content is replaced; shared sessions revive objects deleted before with `Restore`) and `version.delete {id | ids}` (the reply and the change event name what was deleted) are one undo step and one change set each. `version.list` and `version.get {id, document?}` (read only; at most 8 MiB). Versions are local to the file: collaboration does not share them and keeps them when a shared document arrives (REV-09 will share them). A `document.get` then `document.load` round trip keeps the versions (the document has no `history` field, so the session keeps its versions for the new drawing). In a shared session a restore that cannot revive an object that another user deleted says so in its `notes`. The web save writes the file form like the native save. The app has File > Versions... (Save Version, Restore and Delete with a question, Compare, the limit dialog, the read-only notice), in en-US and Estonian, and in both built-in profiles. `crates/kadakas-api/tests/versions_bench.rs` measures the time of create, restore, diff, save and open, the file size and the memory for 1k, 10k and 100k objects and 10, 100 and 1000 versions (`cargo test --release -p kadakas-api --test versions_bench -- --ignored --nocapture`); the limit of a save and the cap of a read count the same things (the change of every version, the change of the newest version, the pictures), the thresholds are cut to what a reader reads at the half (1000 versions, 256 MiB of 512 MiB), so that a file within the limits never opens read only, and the Preferences cannot go above it; the defaults are 1000 versions (`VERSIONS_MAX`, the read cap) and 256 MiB (`WRITE_MAX_BYTES`, the highest safe write limit), so there is no practical count limit (`SessionLimits::strict()` keeps 20 and 16 MiB; a stored preference of 100 or 64 MiB, the old defaults, moves to the new defaults on load). The benchmark above shows that a version adds about 1.7 KB to the file, and that the time grows with the drawing, not with the number of versions. A document that passes 500 versions gets a one-time warning that never blocks: a notice in the app, and `notes` with `many_versions` in the `version.create` reply. Not done: the edit log between versions (only the delta is kept), a rule that keeps named versions longer than unnamed ones, the order of classes and resources is not part of a version, sharing, and merging old versions into one (not needed now). A history whose drawing does not match has no drawing to go back to (the `base` entry exists only for a history that a reader kept while the drawing was still the one it was written against): its versions stay in the file unchanged, but they cannot be rebuilt, and the only way out is `version.repair`. A committed set of files with versions (crates/kadakas-api/tests/data, with a shape value per version, a picture and a `base` entry) must read with no notes in every build: that test guards the format against drift of the document model. Memory: the undo steps share the parts of the history (each version, each operation of the change since the anchor, each picture), so many versions cost the drawing plus the deltas; the operations of the change since the anchor (the drawing when the file was opened) that stay equal are shared too, so the memory grows with what changes between two versions. **Storage in a file (DOC-20 to DOC-22).** In a container the history is in the entries of `history/` (its pictures are entries of `blobs/`, shared with the drawing) and waits in the file until a call uses it (DOC-21): the first use reads it, checks it against the drawing as the file holds it, and notes what it could not read; a history that cannot be read stays in the file and is read only.
